# ADR-028 — Living specs: requirement IDs, a coverage register, and drop-requires-ADR

**Status:** Ratified
**Lock-in phase:** Phase 1 (cross-cutting; binds every spec edit from this point)
**Supersedes:** —

## Context

Plans change during implementation. That is not the problem. The problem is that when they change,
the spec corpus and the code drift apart silently, and the drift is discovered by accident months
later — if at all.

The operator's stated experience: "when i iterate over a spec 20+ times you have a tendency to drop
important information." Three instances surfaced in the 2026-08-08/09 session alone:

1. The Council-Synthesis harness slices were "lost across spec iterations" and had to be recovered
   from a re-upload.
2. A 44-component stack list was supplied more than once; a scan found its memory/retrieval layer
   adopted nowhere, the MCP tool tier dropped wholesale, and graph visualisation absent from every
   surface.
3. Every donor-spec provenance header points at `docs/specs/COVERAGE-forge-oh.md`, which was never
   created. Fourteen files carry a reference to a document that does not exist.

A fourth instance is the same defect in executable form: `provisional_types_not_wired` keyed on a
comment string, the comment was reworded for good reasons, and the gate silently stopped gating
(DEBUG_LOG 2026-08-09 01:30).

`kosmos-spec-diff` already prescribes the correct ritual — cross-check §17 against the ADR files,
keep the fan-out atomic. It is a good procedure and it is not enough, because it is prose. The
consistent lesson of this repo is that **anything not executable eventually stops being true, and
nobody finds out until they happen to look.**

## Decision

1. **Requirement IDs.** Every normative statement in `docs/specs/` carries a stable identifier
   `REQ-<spec>-<nnn>`, where `<spec>` is the spec's numeric prefix (`04`, `04a`) and `<nnn>` is
   zero-padded and assigned in order of first appearance. **An ID is permanent and is never
   reused**, including after the requirement is dropped. Renumbering is forbidden: the whole value
   is that a missing key stays missing.

2. **A coverage register** at `docs/specs/COVERAGE.md`, generated by
   `scripts/spec_coverage.py`. Each ID has exactly one status:

   | Status | Meaning | Evidence required |
   |---|---|---|
   | `SPECCED` | Stated, not yet built | — |
   | `IMPLEMENTED` | Built | a `path:line` or a test name that resolves |
   | `DEFERRED` | Postponed to a named phase | the phase name |
   | `DROPPED` | No longer a requirement | an ADR reference |

3. **Dropping a requirement requires an ADR.** Not a log line. A dropped requirement is the most
   expensive class of change to discover late — it is invisible by construction, since the artifact
   is an absence — and it is precisely the failure the operator raised. The ADR cost is deliberate
   friction on the one operation that otherwise leaves no trace.

4. **Four gates** in the hard-constraints runner, each mutation-tested:
   - `spec_requirements_have_ids` — every normative statement carries an ID, and every ID is
     well-formed and unique.
   - `spec_coverage_register_is_current` — the register lists exactly the IDs present in the specs,
     no more and no fewer.
   - `spec_coverage_evidence_resolves` — every `IMPLEMENTED` evidence path resolves at the cited
     line, and every `DROPPED` ADR reference names an ADR that exists.
   - `spec_cross_references_resolve` — every relative document reference between specs and ADRs
     points at a file that exists. This is the gate that would have caught `COVERAGE-forge-oh.md`.

5. **Retrofit is curate-as-touched, plus one Phase 1 pass.** IDs are assigned by hand to the specs
   Phase 1 work touches, and to any spec at its next edit. Auto-generation from headings and
   keyword matching was rejected: it lands IDs on non-requirements and misses real ones, producing a
   register that looks authoritative and is not — the exact failure mode this ADR exists to prevent.
   Coverage is therefore partial by design, and the register records which specs are enrolled so
   that partial coverage is visible rather than implied.

## Rationale

**Alternative A — rely on `kosmos-spec-diff` and reviewer discipline.** Rejected. It is the status
quo, and the status quo produced all four instances above. The skill is retained as the ritual layer
on top of the gates, not as the enforcement.

**Alternative B — gates without IDs, diffing spec prose between commits.** Rejected. Prose diffs
cannot distinguish a requirement being deleted from a requirement being reworded, and reword is the
common case during iteration. Stable IDs are what make deletion detectable.

**Alternative C — auto-generate IDs across all 16 specs immediately.** Rejected per decision 5.

**Alternative D — track requirements in an external tracker.** Rejected against the local-first,
single-user constraint, and because a tracker is one more surface to drift from.

## Consequences

- `scripts/spec_coverage.py` (new) generates and validates `docs/specs/COVERAGE.md`.
- Four checks added to `scripts/hard_constraints/`, registered as enforced Phase 1 gates, each with
  a mutant proving it can fail.
- `docs/specs/13-hard-constraints.md` gains the four gate rows.
- The 14 donor-spec provenance headers pointing at `COVERAGE-forge-oh.md` are corrected to
  `COVERAGE.md`, resolving a live dangling reference.
- A new OH-GUI skill carries the edit ritual: assign IDs on touch, regenerate the register, never
  renumber, drop only by ADR.
- Requirements dropped before this ADR are unrecoverable by these means. No attempt is made to
  reconstruct them; the register starts from what the specs say today.

## Amendment 1 (2026-08-09 01:50 EDT) — deviation is recorded, not avoided

The operator works under a hard budget constraint: when credits run low, work moves off the spec
sequence and onto whatever has the highest immediate return. His stated experience is that this
"ends up making things more confusing in the end."

The confusion is not caused by working out of order. It is caused by working out of order
**without leaving a trace**, so that later nobody can distinguish a requirement that was skipped
from one that was built, abandoned, or never noticed. That is the same absence-shaped defect as a
dropped requirement, and it has the same remedy.

Therefore:

1. **Out-of-sequence implementation is legitimate and needs no approval.** ROI-driven ordering is a
   valid strategy under a budget, not a failure of discipline.
2. **Every requirement skipped in order carries a `DEFERRED` status with a named phase**, so the
   skip is a recorded state rather than an omission. `spec_coverage.py` already refuses a
   `DEFERRED` row with no phase.
3. **Work stops at a landable boundary, not at exhaustion.** A half-built mechanism that is never
   committed costs more than it returns, because the next session pays to rediscover it. When
   budget is short, the correct final action is to land and record what exists and mark the rest
   `DEFERRED` — not to push one more feature.
4. **The register is the answer to "where were we".** A future session reads statuses instead of
   reconstructing intent from the code, which is the expensive way and the one that drifts.

This amendment is itself an application of clause 3: the four gates in decision 4 are recorded
`DEFERRED` to Phase 1 rather than half-built, because the ids and the register deliver most of the
value on their own and the gates are separable.
